# Technical Landscape: A Local-First, macOS-Native "Granola-Style" Meeting Transcriber (2026)

*Scope: single-developer, fully-local, privacy-sensitive menu-bar app that captures audio from all meeting apps in the background — no bots — and produces speaker-labeled transcripts on-device.*

**A note on evidence weighting (read this first):** The source corpus I was given is deep and well-corroborated on **audio capture, dual-stream, and meeting detection** (sections 1, 2, 5) — most claims there rest on 2–4 distinct sources including Apple's own docs. It is **thinner on the transcription-engine benchmarks and the open-source-clone inventory** (sections 3, 6): I have the primary source URLs the researchers gathered, but the extracted head-to-head numbers (WER/RTF tables) were not present in my evidence excerpts. Where that is the case I cite the source for *what it covers* and explicitly flag that the specific figures must be read off the linked benchmark page rather than trusted from this report. I have not invented any numbers.

## 1. Audio capture on macOS

### How the incumbents capture audio (and Granola's no-bot trick)

Granola's differentiator is that it does **not** join the call as a bot participant. Instead it captures the Mac's audio **at the OS level**: it reads the **system audio output** (the meeting app's playback = everyone else) *plus* the **microphone** (you) simultaneously, sitting *below* the meeting app rather than inside it. That is why it works uniformly across Zoom, Google Meet, Microsoft Teams, Slack huddles, WebEx, FaceTime, and WhatsApp — it never integrates with any of them ([docs.granola.ai/help-center/taking-notes/transcription](https://docs.granola.ai/help-center/taking-notes/transcription); [docs.granola.ai/…/speaker-attribution](https://docs.granola.ai/help-center/taking-notes/speaker-attribution); [docs.granola.ai/…/troubleshooting/transcription-issues](https://docs.granola.ai/help-center/troubleshooting/transcription-issues)). Granola deliberately does **not** publicly name which API it uses (Core Audio tap vs ScreenCaptureKit) — its docs only say configuration "happens at the OS level" (convergent across 3 Granola docs pages). Recall.ai's platform write-ups frame the same two OS-level APIs (Core Audio taps and ScreenCaptureKit) as the modern bot-free capture paths ([recall.ai/blog/macos-screencapture-api](https://www.recall.ai/blog/macos-screencapture-api)).

### The three real options on macOS 26 (2026)

| | **(a) Core Audio Process Tap** | **(b) ScreenCaptureKit (SCStream)** | **(c) Virtual device (BlackHole/Loopback)** |
|---|---|---|---|
| **API entry** | `CATapDescription` → `AudioHardwareCreateProcessTap` → embed tap UID in `AudioHardwareCreateAggregateDevice` → `AudioDeviceCreateIOProcIDWithBlock` | `SCStreamConfiguration.capturesAudio` + `SCStream` + `SCStreamOutput` delegate | Install driver; set system output to a Multi-Output/Aggregate device containing the virtual device; read it as an input |
| **Min macOS** | API since 14.2; **ship ≥14.4** for correct TCC category | System audio since **12.3**; in-stream **mic since 15.0** | n/a (driver) |
| **TCC permission** | **"System Audio Recording"** — its *own* category via `NSAudioCaptureUsageDescription` | **Screen Recording** grant (no separate audio permission, no entitlement) | Microphone (reads the loopback as a mic input) |
| **Privacy indicator** | **Purple** system-audio dot | Persistent **screen-recording** indicator (Sequoia added a menu-bar indicator + periodic re-consent) | Orange mic dot |
| **Per-process vs mixed** | **Per-process** *or* system-wide mixdown (you choose PIDs) | System audio mixed (includes notifications/media); not window-isolated | System output mixdown only |
| **User routing needed?** | No | No | **Yes** — manual routing + driver install |
| **Signing** | **Hard requirement** — unsigned build never fires the prompt | TCC-gated, no signing entitlement | Driver install (admin) |
| **Audio-only?** | Yes (native) | No — must register a video output; hack a 2×2 / low-fps frame | Yes |

Sources for the table rows below.

**(a) Core Audio Process Taps — the modern primary path.** Apple's official guide *"Capturing system audio with Core Audio taps"* gives the exact workflow: build a `CATapDescription` (set `.processes`, `.isPrivate`, `.isMixdown`/`.isMono`, `.muteBehavior`, `.isExclusive`, `.deviceUID`, `.stream`), call `AudioHardwareCreateProcessTap(description, &tapID)`, read the tap UID via `kAudioTapPropertyUID`, and add it to an aggregate via `kAudioAggregateDevicePropertyTapList`; the format comes from `kAudioTapPropertyFormat` and PCM arrives in the IOProc as `float*` ([developer.apple.com/…/capturing-system-audio-with-core-audio-taps](https://developer.apple.com/documentation/CoreAudio/capturing-system-audio-with-core-audio-taps)). The canonical Swift reference is **insidegui/AudioCap** (~506★, "recording system audio on macOS 14.4+"), which uses `kAudioHardwarePropertyTranslatePIDToProcessObject`, `AudioHardwareCreateProcessTap`, `kAudioSubTapUIDKey`/`kAudioAggregateDeviceTapListKey`, and `AudioDeviceCreateIOProcIDWithBlock` ([github.com/insidegui/AudioCap](https://github.com/insidegui/AudioCap)). The directmusic Obj-C gist shows both `initStereoGlobalTapButExcludeProcesses:` (system-wide) and per-process init, plus the aggregate keys `kAudioAggregateDeviceTapListKey`, `kAudioAggregateDeviceTapAutoStartKey`, `kAudioAggregateDeviceIsPrivateKey` ([gist directmusic](https://gist.github.com/directmusic/7d653806c24fe5bb8166d12a9f4422de)). DGR Labs' 2026 build write-up confirms targeting **≥14.4** "keeps you in the right TCC category" ([dgrlabs.co/…/capturing-system-audio-on-macos-in-2026](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html)). *Convergent, 4 sources.* Additional reference implementations: **makeusabrew/audiotee** and the maven.de *"CoreAudio Taps for Dummies"* write-up ([maven.de/2025/04/coreaudio-taps-for-dummies](https://www.maven.de/2025/04/coreaudio-taps-for-dummies/); [github.com/makeusabrew/audiotee](https://github.com/makeusabrew/audiotee)).

**Tap TCC details.** The permission is a *dedicated* category, declared with `NSAudioCaptureUsageDescription` — a key **not** in Xcode's dropdown (enter it by hand). There is **no public API to request or query** the grant; the prompt fires only for a properly code-signed binary with a stable signing identity ("Unsigned xcodebuild builds compile fine but can't actually exercise audio capture — the prompt won't fire"). AudioCap optionally probes it via the private `TCCAccessPreflight`/`TCCAccessRequest` ([Apple guide](https://developer.apple.com/documentation/CoreAudio/capturing-system-audio-with-core-audio-taps); [NSAudioCaptureUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsaudiocaptureusagedescription); [DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html); [AudioCap README](https://github.com/insidegui/AudioCap/blob/main/README.md)). *Convergent, 4 sources.* The consent prompt reads "wants to **record system audio**" (not the alarming "record your screen") — the single biggest UX argument for taps. Reset for testing with `tccutil reset SystemAudioCaptureRequests <bundle-id>`.

**Correction to a common myth — taps are NOT "invisible."** Reading from a tap raises a **purple** system-audio-recording dot (distinct from the orange mic dot and from the screen-recording indicator). The real UX contrast is *purple-audio-dot (taps)* vs *screen-recording-grant + indicator (SCK)*, not indicator-vs-none ([maven.de](https://www.maven.de/2025/04/coreaudio-taps-for-dummies/); [cdm.link/fix-the-orange-dot](https://cdm.link/fix-the-orange-dot/)). *Convergent, 2 sources.*

**⚠ The tap reliability risk (load-bearing for an always-on meeting app).** Apple Developer Forums thread **825780** (May 2026, macOS 26.5 beta, M2 Air, *0 replies / not officially acknowledged*) reports that after minutes of operation `AudioHardwareCreateProcessTap` "transitions into an all-zero state" — the IOProc keeps firing with valid timestamps and buffer sizes, but **every PCM sample is exactly `0.0f` while other apps are still audibly playing.** A 51-minute session logged multiple all-zero windows (60s, 53s, 141s; later 16min, 3min). Suspected triggers: sample-rate renegotiation (44.1↔48 kHz), Bluetooth/AirPods sleep-wake, device routing; MacBook Air affected more than Pro. The only fix is a full **teardown + rebuild** of *both* tap and aggregate (`AudioDeviceStop` → `DestroyIOProcID` → `DestroyAggregateDevice` → `DestroyProcessTap` → recreate all), and the author warns it "cannot be reliably distinguished from legitimate silence," so you cannot auto-detect it cleanly ([Apple Forums 825780](https://developer.apple.com/forums/thread/825780)). DGR Labs independently frames the tap path as "full of traps that aren't documented" — e.g. flipping `tapDescription.isExclusive` after init inverts exclude-vs-only-listed semantics and yields silence while all callbacks fire; a tap-as-main-sub-device with an empty sub-device list also silently yields zeros ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html)). **Status:** the zero-sample defect is essentially **single-source (thread 825780) and beta-only (macOS 26.5)** — treat it as an *unverified-scope reliability risk*, not confirmed on shipping releases, but design a watchdog for it regardless. The "silence traps are real and undocumented" framing is corroborated 2 sources.

**⚠ Teams-specific tap failure (single-source — unverified, but plausible mechanism).** GitHub **pasrom/meeting-transcriber issue #79** reports that a **per-process** `CATapDescription` "captures no audio from Microsoft Teams (app.wav always silent)" — the aggregate builds with no error but delivers zero-filled buffers; the reporter hypothesizes Teams' non-standard WebRTC audio routing evades a per-process tap, and notes that **ScreenCaptureKit-based competitors (Jamie, Muesli) capture Teams fine** ([github.com/pasrom/meeting-transcriber/issues/79](https://github.com/pasrom/meeting-transcriber/issues/79)). This is the strongest single argument for SCK (or a *system-wide mixdown* tap rather than per-process) if Teams must be covered. **Single-source — unverified**, but directly on-point for "capture ALL meeting apps."

**(b) ScreenCaptureKit — the alternative system-audio path.** `SCStreamConfiguration` exposes `capturesAudio`, `sampleRate`, `channelCount` (system audio since 12.3). It is *purely TCC-gated by Screen Recording* — no code-signing entitlement, no separate audio permission ([Apple SCK docs](https://developer.apple.com/documentation/ScreenCaptureKit/capturing-screen-content-in-macos); [recall.ai SCK](https://www.recall.ai/blog/macos-screencapture-api)). A 100%-local build guide sets `capturesAudio=true`, `excludesCurrentProcessAudio=true`, `sampleRate=16000`, `channelCount=1`, `width=2`, `height=2` and warns this "requires Screen Recording permission, even though no screen is recorded — a major friction point" ([dev.to/thehwang](https://dev.to/thehwang/building-a-100-local-meeting-transcription-app-for-macos-with-whispercpp-and-screencapturekit-33m7)). *Convergent, 4 sources.* Costs beyond the scary grant: you **cannot go audio-only** — without an `.screen` output SCK errors ("stream output NOT found"), so you must register a token video output and set a very low `minimumFrameInterval`; macOS Sequoia added a persistent menu-bar indicator and periodic re-consent nags; and SCK's audio "is not isolated" (can include notifications/media) ([Apple SCK](https://developer.apple.com/documentation/screencapturekit/); [recall.ai record-a-meeting](https://www.recall.ai/blog/how-to-use-screencapturekit-to-record-a-meeting); [screenify.studio permissions](https://www.screenify.studio/blog/2026-04-23-macos-screen-recording-permissions)).

**⚠ Contradiction inside Apple's own docs (decisive for your min-OS choice).** The **aggregated** `SCStreamConfiguration` page reports all six audio properties — including `captureMicrophone`, `SCStreamOutputType.microphone`, and `excludesCurrentProcessAudio` — as available since **12.3**. The **per-symbol availability JSON** contradicts this: `captureMicrophone` and `SCStreamOutputType.microphone` are **15.0**; `microphoneCaptureDeviceID` is **15.0**; `excludesCurrentProcessAudio` is **13.0** ([captureMicrophone.json](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scstreamconfiguration/capturemicrophone.json); [microphone.json](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scstreamoutputtype/microphone.json); [excludescurrentprocessaudio.json](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scstreamconfiguration/excludescurrentprocessaudio.json)). **Resolution: trust the per-symbol JSON.** If you want mic + system audio inside one SCStream you need a **macOS 15.0 floor**; on <15 you must capture the mic separately via AVAudioEngine. Building against the 12.3 claim would break on 12.3–14.x. *Convergent, 4 sources; contradiction explicitly flagged.*

**(c) Virtual audio devices — legacy fallback, not recommended as primary.** **BlackHole** (ExistentialAudio) is "a modern macOS audio loopback driver … with zero additional latency," but its own docs require building a Multi-Output or Aggregate device to both hear *and* capture, with "Built-in Output/Microphone … listed as the top device," "Drift Correction for all devices except the Clock Source," and warnings that AirPods' lower sample rate must not be the clock ([github.com/ExistentialAudio/BlackHole](https://github.com/ExistentialAudio/BlackHole); [Aggregate-Device wiki](https://github.com/ExistentialAudio/BlackHole/wiki/Aggregate-Device); [deepwiki BlackHole 3.2](https://deepwiki.com/ExistentialAudio/BlackHole/3.2-multi-output-and-aggregate-devices)). *Convergent, 3 sources.* This means a driver install **and** manual user routing — exactly the "silent background, no setup" UX that Granola-style apps exist to avoid. Use only as a compatibility escape hatch.

**Recommendation for section 1:** primary = **Core Audio Process Tap (system-wide mixdown, ≥14.4, signed/notarized)** for the clean audio-only consent story, with a **watchdog + full rebuild** to survive the zero-sample bug; keep **ScreenCaptureKit (≥15.0)** as the fallback specifically because it is the one confirmed to capture Teams. This mirrors what Jamie/Muesli chose for Teams robustness.

## 2. Dual-stream capture (mic + system output, kept separate for diarization)

**Best practice — one aggregate device, one clock.** The cleanest, drift-free approach is a **single `AudioHardwareCreateAggregateDevice`** that contains **both** the built-in microphone (as an input sub-device) **and** the process tap (as a sub-tap). One IOProc then delivers **channel 0 = mic (you)** and **channel 1 = system output (everyone else)** on one shared clock, eliminating cross-stream drift; set per-sub-device drift compensation (`kAudioSubDeviceDriftCompensationMaxQuality`) on the non-clock device ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html); [directmusic gist](https://gist.github.com/directmusic/7d653806c24fe5bb8166d12a9f4422de)). *Convergent, 2 sources.* This is the highest-value architectural decision in the whole app: because your channels are physically separated (mic = you, system = others), you get **channel-based diarization "for free"** for the two-way you-vs-them split, before any neural diarizer runs.

**If you instead run two separate streams** (e.g. SCK `.microphone` + `.audio`, or SCK-system + AVAudioEngine-mic), they are on **independent clocks** and you must align timestamps yourself: capture each stream's *first* `presentationTimeStamp` and subtract it from all later timestamps, and **never interleave** buffers of differing sample rate / channel count into one writer/track ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html); Apple SCK per-symbol docs). *Convergent, 2 sources.* Drift over a long meeting will otherwise smear speaker attribution.

**Echo / AEC — a hard part with no native fix.** No macOS capture API provides acoustic echo cancellation, and mixing mic + speaker capture creates echo (in the Teams issue above, speaker bleed into the mic initially *masked* the fact that the tap was delivering silence). Best practice for the mic path is **AVAudioEngine with Voice-Processing IO** (voice processing enabled), which supplies AEC — but note it can emit a multi-channel (e.g. 9-channel) format that you must **down-mix to mono 16 kHz manually** (`AVAudioConverter` has reportedly crashed on that format for some builds) ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html); Apple audio docs referenced therein). *Convergent, 2 sources.* Using headphones sidesteps most echo; over speakers, Voice-Processing IO on the mic is the recommended mitigation.

## 3. Local transcription on Apple Silicon (2026)

**Evidence caveat:** the corpus gathered the primary sources below but the extracted head-to-head **WER/RTF tables were not present in my evidence excerpts.** I therefore give the option map and qualitative positioning with citations to where the numbers live, and flag specifics as needing verification against the linked pages rather than asserting figures.

**The engine options and their primary sources:**

- **Apple SpeechAnalyzer / `SpeechTranscriber`** (new on-device framework, macOS 26 / iOS 26). This is the native, no-model-download, streaming-capable path. Apple's docs and WWDC 2025 session 277 ("advanced speech-to-text") are authoritative ([developer.apple.com/documentation/speech/speechanalyzer](https://developer.apple.com/documentation/speech/speechanalyzer); [bringing-advanced-speech-to-text-capabilities](https://developer.apple.com/documentation/Speech/bringing-advanced-speech-to-text-capabilities-to-your-app); [WWDC2025/277](https://developer.apple.com/videos/play/wwdc2025/277/); community walkthroughs [dev.to/arshtechpro WWDC2025](https://dev.to/arshtechpro/wwdc-2025-the-next-evolution-of-speech-to-text-using-speechanalyzer-6lo) and [antongubarenko iOS 26 SpeechAnalyzer guide](https://antongubarenko.substack.com/p/ios-26-speechanalyzer-guide)). **Convergent claim (2+ sources):** Apple's new foundation-model speech APIs are reported to **outpace Whisper for transcription speed** ([daringfireball.net linked 2025-06-19](https://daringfireball.net/linked/2025/06/19/apples-new-foundation-model-speech-apis-outpace-whisper-for-transcription); corroborated by the WWDC session and the dev.to/arshtechpro walkthrough). For a native menu-bar app this is the lowest-friction, lowest-memory default on macOS 26.
- **whisper.cpp** — GGML C/C++ Whisper, Metal-accelerated ([github.com/ggml-org/whisper.cpp](https://github.com/ggml-org/whisper.cpp)); it is the engine the thehwang 100%-local build pairs with ScreenCaptureKit ([dev.to/thehwang](https://dev.to/thehwang/building-a-100-local-meeting-transcription-app-for-macos-with-whispercpp-and-screencapturekit-33m7)).
- **WhisperKit** (argmax) — Whisper on Core ML / Apple Neural Engine, the standard Swift-native Whisper path ([github.com/argmaxinc/WhisperKit](https://github.com/argmaxinc/WhisperKit)).
- **faster-whisper** (SYSTRAN, CTranslate2) — the fast Python/CTranslate2 implementation ([github.com/SYSTRAN/faster-whisper](https://github.com/SYSTRAN/faster-whisper)); a 2026 comparison with whisper.cpp lives at [codersera.com/blog/faster-whisper-vs-whisper-cpp-2026](https://codersera.com/blog/faster-whisper-vs-whisper-cpp-speech-to-text-2026/) *(read the numbers there — not extracted here; treat as single-source)*.
- **NVIDIA Parakeet / Canary via MLX** — `parakeet-mlx` and the **FluidInference/FluidAudio** Swift package, which ships Parakeet + on-device speaker diarization with a published benchmark ([github.com/FluidInference/FluidAudio](https://github.com/FluidInference/FluidAudio); [Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)). FluidAudio is the most directly relevant "native Swift, Apple-Silicon, ASR+diarization in one library" option for this app.
- **Speed harness:** `anvanvan/mac-whisper-speedtest` is a repo dedicated to benchmarking Whisper variants on Mac ([github.com/anvanvan/mac-whisper-speedtest](https://github.com/anvanvan/mac-whisper-speedtest)) — the right place to get your own RTF numbers on your hardware rather than trusting third-party tables. Supporting research (Parakeet/streaming ASR) appears in the arXiv preprints gathered ([2507.18446](https://arxiv.org/pdf/2507.18446), [2509.14128](https://arxiv.org/html/2509.14128v1), [2509.26177](https://arxiv.org/html/2509.26177v1)) *(topic sources; specific results not extracted here)*.

**Diarization options:**
- **Channel-based (recommended for the 2-way split):** because your dual-stream aggregate already separates you (mic) from everyone-else (system), you get robust "self vs others" attribution *without* a neural diarizer. Multichannel separation is explicitly positioned as more reliable than acoustic diarization when channels are physically distinct ([deepgram.com/learn/multichannel-vs-diarization](https://deepgram.com/learn/multichannel-vs-diarization); [docs.recall.ai/docs/diarization](https://docs.recall.ai/docs/diarization)). Granola itself leans on this "who is speaking" split via device audio ([Granola speaker-attribution](https://docs.granola.ai/help-center/taking-notes/speaker-attribution)).
- **Neural diarization for the "others" channel (multiple remote speakers on one system stream):** **NVIDIA Streaming Sortformer** is purpose-built for real-time speaker ID in meetings ([developer.nvidia.com/blog/…streaming-sortformer](https://developer.nvidia.com/blog/identify-speakers-in-meetings-calls-and-voice-apps-in-real-time-with-nvidia-streaming-sortformer/)); **FluidAudio** provides on-device diarization in Swift ([FluidAudio](https://github.com/FluidInference/FluidAudio)); Speechmatics documents production diarization behavior/tradeoffs ([docs.speechmatics.com/…/diarization](https://docs.speechmatics.com/speech-to-text/features/diarization)). *pyannote* is the usual open-source neural diarizer named in the brief, but I have **no distinct source for it in this corpus** — treat any pyannote-specific claim as **not established by this evidence set**.

**Practical read:** on macOS 26, start with **Apple SpeechTranscriber** (native, streaming, fast, zero model management) for the transcript, and use **channel-based diarization** from your dual-stream capture for the you-vs-them label. Add **FluidAudio/Sortformer** neural diarization only if you need to split multiple remote participants on the single system-audio channel. Validate any engine choice with `mac-whisper-speedtest` / FluidAudio's Benchmarks.md on *your* machine.

## 4. Streaming vs batch (live vs post-meeting)

The corpus supports the following qualitative tradeoffs (primary sources for streaming are the SpeechAnalyzer/`SpeechTranscriber` docs and WWDC 2025/277, which is explicitly a *streaming* analyzer API):

- **Streaming (live):** lowest perceived latency and enables live UI, but partial hypotheses get revised as more context arrives, so you must render "volatile" text and reconcile corrections. SpeechAnalyzer is designed for this incremental model ([developer.apple.com/documentation/speech/speechanalyzer](https://developer.apple.com/documentation/speech/speechanalyzer); [WWDC2025/277](https://developer.apple.com/videos/play/wwdc2025/277/)).
- **Batch (post-meeting):** best accuracy (full-context decoding, larger models feasible, easier diarization over the whole recording) at the cost of no live feedback. whisper.cpp/faster-whisper/WhisperKit are all commonly run batch.
- **Hybrid (what Granola-style apps do):** show a fast live stream during the call, then optionally re-transcribe the buffered audio in batch afterward for the clean saved transcript and AI notes. This matches Granola's model of a live transcript plus post-call notes ([Granola transcription](https://docs.granola.ai/help-center/taking-notes/transcription)).

*This section is the least deeply-corroborated in my excerpts — the latency/UX framing is standard and source-grounded, but I did not receive extracted numeric latency claims. Treat specifics as design guidance, not measured facts.*

## 5. Meeting detection (auto-start capture)

**Mic-in-use (Core Audio).** Register a property listener for **`kAudioDevicePropertyDeviceIsRunningSomewhere`** (scope `kAudioObjectPropertyScopeGlobal`) via **`AudioObjectAddPropertyListenerBlock`** on each audio device — you get a callback whenever *any* process starts/stops the mic. Query current state synchronously with `AudioObjectGetPropertyData` on the same selector. Enumerate devices with `AVCaptureDevice.devices(for: .audio)` and obtain each device's `AudioObjectID` via the private `connectionID` selector ([github.com/objective-see/OverSight](https://github.com/objective-see/OverSight); [gist metrovoc](https://gist.github.com/metrovoc/0b5e3590c6069cf99b01559863bc2ce4)). *Convergent, 2 sources.*

**Camera-in-use (CoreMediaIO).** The camera equivalent uses **`CMIOObjectAddPropertyListenerBlock`** with the **same** selector `kAudioDevicePropertyDeviceIsRunningSomewhere` — CoreMediaIO reuses the Core Audio constants; there is no dedicated video constant — on each video device's `CMIOObjectID`. Enumerate cameras with `AVCaptureDevice.devices(for: .video)`. **Camera + mic on together, inside a known meeting app, is a strong low-false-positive meeting signal** ([objective-see/OverSight](https://github.com/objective-see/OverSight); [gist metrovoc](https://gist.github.com/metrovoc/0b5e3590c6069cf99b01559863bc2ce4)). *Convergent, 2 sources.*

**Which process turned it on?** Neither the Core Audio nor CoreMediaIO run-state callbacks tell you the owning process. To attribute the session to Zoom/Teams/Meet you must **scrape the macOS unified log**: start an `OSLogEventLiveStream` filtered to subsystems `com.apple.cmio` (camera) and `com.apple.coremedia` (mic) and regex out the PID. This relies on **private LoggingSupport APIs and undocumented log formats** — brittle across OS updates ([objective-see/OverSight](https://github.com/objective-see/OverSight); [gist metrovoc](https://gist.github.com/metrovoc/0b5e3590c6069cf99b01559863bc2ce4)). *Convergent, 2 sources.* A more robust, App-Store-safe alternative for app attribution is enumerating running/audible processes via **ScreenCaptureKit's `SCShareableContent`** application list, or matching against a bundle-ID allowlist (Zoom `us.zoom.xos`, Teams, Chrome hosting Meet, Slack) — combine "mic is running" + "a known meeting app is frontmost/audible" to trigger.

## 6. Existing open-source clones worth forking / learning from

*Star counts and languages are given only where the evidence stated them; otherwise I name the repo and its relevance without inventing metrics.*

- **insidegui/AudioCap** (~506★, Swift) — *the* reference for Core Audio process taps on 14.4+. Not a full app, but the correct, idiomatic tap + aggregate + IOProc implementation to copy ([github.com/insidegui/AudioCap](https://github.com/insidegui/AudioCap)). **What it got right:** clean tap lifecycle, private-TCC preflight. **Limit:** system-audio only, no transcription.
- **pasrom/meeting-transcriber** — a real tap-based meeting transcriber; its **issue #79** is the canonical evidence that per-process `CATapDescription` fails on Teams ([github.com/pasrom/meeting-transcriber](https://github.com/pasrom/meeting-transcriber), [issue #79](https://github.com/pasrom/meeting-transcriber/issues/79)). **Learn from its mistake**, don't repeat per-process tapping for Teams.

## 7. Recommended reference architecture (menu-bar background app)

```
                         ┌────────────────────────────────────────────┐
  Meeting detector  ───▶ │  TRIGGER: mic-running (kAudioDevice…IsRunning)
  (Core Audio +          │           + known meeting app audible/front
   CoreMediaIO listeners)└───────────────┬────────────────────────────┘
                                         ▼
   CAPTURE LAYER  ── single AGGREGATE DEVICE ──────────────────────────
   ├─ ch0: built-in mic  (AVAudioEngine Voice-Processing IO → AEC → mono16k)
   └─ ch1: process tap   (system-wide mixdown, ≥14.4, signed)
        one IOProc, one clock  →  drift-comp on non-clock sub-device
                                         │  (fallback: SCStream ≥15.0 for Teams)
                                         ▼
        RING BUFFER (lock-free, per-channel)  +  WATCHDOG
          └─ detects zero-sample bug → full teardown+rebuild of tap+aggregate
                                         ▼
        TRANSCRIPTION WORKER  (off the audio thread)
          ├─ live:  SpeechTranscriber (streaming, macOS 26)
          ├─ batch: whisper.cpp / WhisperKit / Parakeet(FluidAudio) re-pass
          └─ diarization: channel-based (you=ch0 / others=ch1)
                          + Sortformer/FluidAudio only to split ch1
                                         ▼
        STORAGE  transcripts + timestamps + speaker labels
                 (local SQLite/files)  →  optional later AI-notes pass
                                         ▼
        MENU-BAR UI  (status, live transcript, history)
```

**The hard parts, ranked (all evidence-backed above):**
1. **Tap zero-sample silence bug** → mandatory watchdog + full tap/aggregate rebuild; you cannot distinguish it from real silence, so use a heuristic (long silence *while* the meeting app is known-audible) to trigger a rebuild ([Apple Forums 825780](https://developer.apple.com/forums/thread/825780)).
2. **Teams capture** → per-process taps fail; use **system-wide mixdown tap** or **SCK ≥15.0** for Teams ([issue #79](https://github.com/pasrom/meeting-transcriber/issues/79)).
3. **Signing/notarization is a precondition, not polish** → taps' TCC grant is keyed to a stable signing identity; an unsigned build never prompts ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html); [AudioCap](https://github.com/insidegui/AudioCap)).
4. **Clock/drift** → prefer the single-aggregate one-clock design; if two streams, align on first-buffer PTS and never interleave mismatched formats ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html)).
5. **Echo** → Voice-Processing IO on the mic; handle its multi-channel output down-mix carefully (`AVAudioConverter` crash risk) ([DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html)).
6. **Permission UX** → one clean "record system audio" prompt (purple dot) for taps beats SCK's screen-recording grant; if you must use SCK for Teams, explain the screen-recording ask ([maven.de](https://www.maven.de/2025/04/coreaudio-taps-for-dummies/); [cdm.link](https://cdm.link/fix-the-orange-dot/)).

## Contradictions & remaining uncertainties (honest ledger)

1. **SCStreamConfiguration availability — resolved.** Apple's aggregate doc page (all audio properties "12.3") conflicts with the per-symbol JSON (`captureMicrophone`/`.microphone` = **15.0**, `excludesCurrentProcessAudio` = **13.0**). Trust the per-symbol JSON → **15.0 floor** for in-stream mic. *Both sides are Apple's own docs; treat the aggregate page as stale.*
2. **Tap "production-ready" vs zero-sample bug — unresolved-scope.** DGR Labs/AudioCap frame taps as ship-ready ≥14.4; thread 825780 shows a hard reliability defect. But that defect is **single-source and beta-only (macOS 26.5)** — I cannot confirm it on shipping releases. **Design defensively (watchdog) but do not treat the bug as universal.**
3. **14.2 vs 14.4 minimum — minor.** API exists at 14.2; correct TCC category/prompt copy requires ≥14.4. Practical floor: **14.4** ([Apple guide](https://developer.apple.com/documentation/CoreAudio/capturing-system-audio-with-core-audio-taps) vs [DGR Labs](https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html)).
4. **Single-source, load-bearing claims (flagged):** the **Teams per-process tap failure** (pasrom #79 only); the **zero-sample silence bug** (thread 825780 only, beta); the **faster-whisper vs whisper.cpp** numbers (codersera only — verify on-device). Treat all three as *plausible/unverified* pending independent confirmation.
5. **Not established by this evidence:** exact **WER/RTF benchmark numbers** for whisper.cpp / MLX / Parakeet / SpeechAnalyzer (I have the benchmark *pages* — FluidAudio Benchmarks.md, mac-whisper-speedtest, codersera — but not extracted figures); **pyannote** specifics (no distinct source in this corpus); Granola's exact internal API (deliberately undisclosed by Granola). Run your own benchmarks with `mac-whisper-speedtest` / FluidAudio before committing an engine.

**Bottom line:** Build on a **signed, notarized, ≥14.4 Core Audio process-tap** (system-wide mixdown) fused with a **Voice-Processing-IO mic into one aggregate device** for drift-free dual-stream capture and free you-vs-them diarization; add a **zero-sample watchdog**; keep **ScreenCaptureKit ≥15.0 as the Teams fallback**; transcribe with **Apple SpeechTranscriber (live) + a batch Whisper/Parakeet re-pass**; and copy the tap plumbing from **insidegui/AudioCap** and the SCK/Teams path from **Muesli**, while treating **pasrom/meeting-transcriber #79** as the cautionary tale.
